# 日次バッチの実行モデル

## 解決したい構造上の問題

反応の数は時間とともに増えるので、**同じ投稿を何度も測り直す**必要がある。
素朴に作ると「測り直すほど費用が増える」構造になり、精度と費用が正面から衝突する。

X API の課金には**同じ資源を 24 時間 UTC 以内に何度読んでも 1 回しか課金されない**
という性質がある。ここに乗せると、**費用を決めるのは取得の頻度ではなく
「1 つの投稿を何日間追いかけるか」**になり、精度と費用の衝突が解ける。

## 構成

| 要素 | 責務 | 責務でないこと |
| --- | --- | --- |
| 時刻起動トリガー | 1 日 1 回、処理を開始する | 正確な時刻の保証。実行は指定時刻から最大 1 時間ずれる |
| 取得の窓 | 追跡期間内に投稿されたものだけを要求する | 取得後の絞り込み。窓の外は最初から要求しない |
| 通知ログ | どの投稿をどの段階まで通知したかを保持する | 判定そのもの |

## 境界

**1 回の実行は独立している。** 前回の実行結果に依存する状態はメモリに持たず、
すべてスプレッドシートから読み直す。途中で落ちても、次の実行が同じ状態から再開する。

**同じ日に 2 回動いても壊れない。** 取得は追加課金されず、通知は通知ログを見て
既に送った段階を飛ばす。二重に鳴ることはない。

## 前提と制約

- **費用は「1 日に読む別々の投稿の数」だけで決まる。** 取得の頻度を落としても
  投稿は結局 1 回は読むので、費用はほとんど下がらない。効くのは追跡を打ち切る日を
  早めることだけ（[[ADR-0003]]）
- **実行時刻は指定した時刻から最大 1 時間ずれる。** Apps Script の仕様であり、
  これ以上の精度は出せない。反応の数を測るのに分単位の精度は要らない
- 取得は 1 回で最大 100 件。追跡期間内の投稿がこれを超える場合はページングする。
  上限に達したら取りこぼしの可能性として扱う（[[UC-03]]）
