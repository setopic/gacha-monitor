# 日次バッチの実行モデル

## 解決したい構造上の問題

反応の数は時間とともに増えるので、**同じ投稿を何度も測り直す**必要がある。
素朴に作ると「測り直すほど費用が増える」構造になり、精度と費用が正面から衝突する。

X API の課金には**同じ投稿を短い間隔で何度読んでも 1 回しか課金されない**
という性質がある。ここに乗せると、**費用を決めるのは取得の頻度ではなく
「1 つの投稿を何日間追いかけるか」**になり、精度と費用の衝突が解ける。

**その単位と、前提が崩れる条件は [CON-01](../40-contracts/con-01-x-api-fetch.md) が規定する。** ここでは繰り返さない。

## 構成

| 要素 | 責務 | 責務でないこと |
| --- | --- | --- |
| 時刻起動トリガー | 1 日 1 回、処理を開始する | 正確な時刻の保証（揺れの幅は「前提と制約」に書く） |
| 取得の窓 | 追跡期間内に投稿されたものだけを要求する | 取得後の絞り込み。窓の外は最初から要求しない |
| 通知ログ | どの投稿をどの段階まで通知したかを保持する | 判定そのもの |

## 境界

**1 回の実行は独立している。** 前回の実行結果に依存する状態はメモリに持たず、
すべてスプレッドシートから読み直す。途中で落ちても、次の実行が同じ状態から再開する。

**同じ日に 2 回動いても壊れない。** 通知は通知ログを見て既に送った段階を飛ばすので、
二重に鳴ることはない。取得のほうは、2 回が課金の単位（[CON-01](../40-contracts/con-01-x-api-fetch.md)）の内側に
収まっていれば追加課金にならない。**その単位は UTC 基準で、実行基盤の日付とは違う。**

## 前提と制約

- **費用は「1 日に読む別々の投稿の数」だけで決まる。** 取得の頻度を落としても
  投稿は結局 1 回は読むので、費用はほとんど下がらない。効くのは追跡を打ち切る日を
  早めることだけ（[ADR-0003](../50-adr/adr-0003-tracking-window.md)）
- **実行時刻は指定した時刻から最大 1 時間ずれる。** Apps Script の仕様であり、
  これ以上の精度は出せない。反応の数を測るのに分単位の精度は要らない
- 取得は 1 ページ 100 件で、**3 ページ（300 件）でページングを打ち切る。**
  打ち切った時点でまだ続きがあれば、取りこぼしの可能性として扱う（[UC-03](../30-usecases/uc-03-alert-anomaly.md)）。
  **「1 ページの上限」と「打ち切りの上限」は別のもの**で、取りこぼすのは後者だけ
  （[CON-01](../40-contracts/con-01-x-api-fetch.md)）
