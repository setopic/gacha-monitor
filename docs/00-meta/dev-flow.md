# 開発の流れ

**この文書はプロジェクトごとに書き換えてよい。** `.gitattributes` の `merge=ours`
が守っているので、テンプレートの更新で上書きされない。ここにあるのは**既定値**であって、
破ると壊れる規約ではない。**壊れるものは `check` と CI が見ている。**

## 順番

```
issue ──▶ grill ──▶ 文書（ADR / UC / DOM）──▶ 実装 ──▶ CI ──▶ main
  │         │              │                    │
  問い      決定           残るもの             implemented_by で文書から指す
```

**この順番が守っているのは 1 つだけである。決まる前に書き始めない。**
書いてから直すと、ADR が「決めた記録」ではなく「揺れた記録」になる。

## 1. issue を立てる

`.github/ISSUE_TEMPLATE/requirement.md` を使う。**issue が持つのは
「まだ答えが無い問い」だけ**で、受け入れ条件も決定も持たない（[META-04](./implementation-layout.md)）。

## 2. grill で詰める

**次の 4 つの場面では、書き始める前に `/grill` を回す。**

| いつ | 合図 | 回さないと何が起きるか |
| --- | --- | --- |
| **issue を書く前** | 「決めること」が 3 つ以上ある、または埋められない | 問いのつもりが解決策の押し付けになる。最初に思いついた案が唯一の案として扱われる |
| **ADR を起こす前** | **却下した案が書けない** | ADR が「決めた記録」ではなく「揺れた記録」になる |
| **実装に着手する前** | ユースケースの「受け入れ条件」が空、または検証できない書き方 | 完成の判定を実装者が後から決めることになる |
| **`schema.py` の語彙・層を変える前** | ノード種別・エッジ種別・層に手を入れようとしている | **全ノードに波及し、取り込む側に移行作業が要る**（major）。着手してからでは戻せない |

**「却下した案が書けない」が最も分かりやすい合図である。**
対案を検討していない決定は、決定ではなく成り行きである。

終わる条件はスキル側にある（`.claude/skills/grill/SKILL.md`）。
要点は **frontier が空**、つまり黙って仮定したものが 1 つも無い状態。

## 3. 決まったことを文書へ移す

**行き先の表は [META-04](./implementation-layout.md) にある。ここでは繰り返さない。**

**issue を閉じるのはここである。** 実装が終わったときではない。
issue が持っていた問いに答えが出た時点で、issue の役目は終わっている。

## 4. 実装する

- **モジュールの説明の 1 行目にノード id を書く。** `implemented_by` の根拠になる
- **識別子はドメインの用語表に合わせる。** `G013` はコードに届かないので、書くときに合わせる
- **文書と実装は同じコミットに入れる。** リポジトリを分けると原理的にできないことで、
  同居させている理由そのものである（[META-04](./implementation-layout.md)）

## 5. PR を出すか、main へ直接出すか

**現状はすべて main への直接 push である**（PR 0 件、タグ 0 件、ブランチは `main` だけ）。
単独で開発しているので、それで困っていない。

ただし **PR のときにしか動かない検査が 2 つある。**

| 検査 | 何を見る | 直接 push だと |
| --- | --- | --- |
| `check --since origin/<base>` | **`G015`（追従漏れ）の窓が base まで広がる** | 未コミットの変更しか見ない。**コミットしてしまうと見えなくなる** |
| `app-check.yml` の `refs` | 変更が実在するノード id を指しているか | 走らない |

だから**次のときはブランチを切って PR にする。**

- **grill を回した変更**（＝ノードを増やした、決定を変えた）
- **`schema.py` の語彙・層を変えた**
- **複数のノードにまたがる変更**

**それ以外は main へ直接でよい。** 誤字の修正に PR は要らない。
**PR を全部に強制すると、上の 2 つの検査が「いつもの儀式」になって読まれなくなる。**

ブランチ名は**ノードの id から取る**。`dom-07-cancel-booking` のように。
どのノードの話かがブランチ名で分かると、`G015` に挙がったときに照合できる。

## 6. コミットとマージ

- **1 行目に何をしたかと、関係するノードの id を書く。** 実測で、この慣習は
  既に成立していた（tournament で 95%、medieval-idle で 100%）
- **`git add -A` を使わない。** 同じリポジトリを別のセッションが触っていることがある。
  自分が作ったファイルを名指しで足す

**人間のレビュアーは置いていない。** 単独開発なので関門は CI である。
複数人になったら `CODEOWNERS` を置き、この節を書き換える。

`--strict`（警告も失敗として扱う）が効くのは **main への push だけ**。
ブランチと PR では警告を出すだけにして、書いている途中で止めない。

## リリースと配置

**タグは打っていない。** 版で参照する必要が出ていないためで、
必要になったら打つ。**打っていないことを既定値として書いておく**のは、
「打ち忘れている」のか「打たない方針」なのかを後から区別するためである。

**履歴は 3 つに分かれていて、持ち主が違う**（表の 4 行目は履歴ではなく、配置の手順の行き先である）。

| 何を | どこに書くか |
| --- | --- |
| 検証ツールの層（`graph-doc-template`）の変更 | `TEMPLATE_CHANGELOG.md` と `tools/graph/version.py`（SemVer） |
| 統合型の層（`graph-project-template`）の変更 | `PROJECT_TEMPLATE_CHANGELOG.md` |
| **このプロジェクト自身の変更** | **`PROJECT_CHANGELOG.md`** |
| 配置の手順 | ユースケース（`usecase-runbook` 雛形） |

**上 2 つはテンプレートの層の履歴で、マージで流れてくる。**
派生プロジェクトが書くのは `PROJECT_CHANGELOG.md` だけである。

**配置は自動と手動の両方がある。** CI から送るもの（GAS への `clasp` など）と、
手順書に沿って人が送るもの（ホストへの配置など）がある。
**どちらも文書があること**が条件で、手順が文書に無い配置は行わない。

## 機械で強制できないもの

**grill を回したかどうかは CI から見えない。** 回した証跡はチャットにしか残らず、
ADR に「grill した」と書いても、それが本当かは確かめられない。

だから上の表は「回さないと何が起きるか」まで書いてある。
**強制ではなく、代償を先に見せる形にしてある。**

同じ理由で次も機械では見ていない。**目で見るしかない。**

| 見ていないもの | なぜ |
| --- | --- |
| ブランチを切ったか | 直接 push を禁じていない |
| コミットの粒度 | 「文書と実装を同じコミットに」は測れない |
| `10-architecture` の用語 | 依存の向きの都合で `G013` が届かない |
| 実装の識別子と用語表の一致 | `G013` は文書の本文だけを見る |

## この既定値を変えるとき

**この文書を書き換えればよい。** `merge=ours` があるので、
テンプレートの更新で戻されることはない。

ただし**変えたことを `PROJECT_CHANGELOG.md` に書く。**
既定値との差は、後から来た人には見えない。
