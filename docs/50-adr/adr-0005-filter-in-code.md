# 転載と返信をコード側で除外する

- 日付: 2026-09-10
- 状態: stable

## 背景

追跡したいのは監視対象が自分で書いた商品告知だけである。
転載・引用・返信は対象外にしたい。理由は 2 つ。

1. **転載された投稿は、仕様上すべての指標が 0 を返す。** 元の投稿の数字を得るには
   参照先を展開する必要があり、展開した投稿にも別途課金される
2. 引用と返信は商品の告知ではない

取得元の API には除外の指定があり、当初はそれに任せる設計にしていた。

## 決定

**API の除外指定は付けるが、それに頼らない。** 取得した投稿を
「参照している投稿」の内容で判定し、**自作でないものはコード側で確実に落とす。**

## 理由

検証で実際に取得したところ、**除外を指定した返信が 2 件返ってきた。**
指定が効いていない。

| 種別 | 100 件中 |
| --- | --- |
| 自作 | 91 |
| 転載 | 6 |
| 引用 | 1 |
| 返信 | 2 |

指定が効かない理由は特定していない（自分への連続投稿は返信として扱われるが
除外されない、という可能性がある）。**原因が分からないまま外部の指定に
依存することはできない。**

一方で、除外の指定を外す理由も無い。**効けば返ってくる件数が減り、
そのぶん課金も減る。** だから「指定は付けるが、保証はコード側で取る」の
二段構えにする。

## 却下した案

| 案 | 却下理由 |
| --- | --- |
| API の除外指定だけに任せる | **実測で効いていない。** 対象外の投稿が判定に混ざる |
| 除外指定を外し、コード側だけで落とす | 返ってくる件数が減らず、落とす分まで課金される |
| 転載も参照先を展開して判定に含める | 費用が最大 2 倍。しかも測るのは他人の投稿の反応になり、監視対象の告知ではなくなる |

## 影響

- [DOM-01](../20-domain/dom-01-post.md): 自作でない投稿は追跡しないことを不変条件にする
- [CON-01](../40-contracts/con-01-x-api-fetch.md): 除外の指定を入力に含めつつ、出力に対象外が混ざる前提で書く

**転載が実質存在しない監視対象なら、この判定で失うものは無い。**
実測では 100 件中 6 件で、いずれも商品告知ではなかった。

## 見直しの条件

- 提供元の除外指定が確実に効くようになったと確認できたとき（それでもコード側の
  判定は残す。二段構えのコストはほぼ無い）
- 監視対象が転載を主体とする運用に変わったとき。そのときは
  「何を測っているのか」から問い直す必要がある
