# 実行基盤に Apps Script を選ぶ

- 日付: 2026-09-09
- 状態: stable

## 背景

必要なのは「1 日 1 回、外部から読んで、記録して、通知する」だけ。
受信する口は要らず、常駐も要らない。

一方で、記録先はスプレッドシートだと最初から決まっていた。
販売店の担当者が中身を見て、閾値を自分で調整できる必要があるからである。

## 決定

**Google Apps Script を実行基盤にし、記録先のスプレッドシートに紐づけて動かす。**

## 理由

- **記録先と実行基盤が同じ場所にある。** 認証も接続設定も要らない
- **無料。** 1 日 1 回の実行は、無料の枠に対して桁で余裕がある
- **時刻起動が標準で付いている。** 別に常駐サーバもスケジューラも要らない
- **担当者が同じ画面で設定を変えられる。** 閾値の調整に開発者を挟まない

制約は把握したうえで受け入れている。

| 制約 | 影響 |
| --- | --- |
| 実行時刻が指定から最大 1 時間ずれる | 反応の数を測るのに分単位の精度は要らない |
| 1 回の実行は 6 分まで | 1 日 100 件程度の取得には十分 |
| 時刻起動の合計が 1 日 90 分まで（無料） | 1 日 1 回なら問題にならない |
| 外部への接続が 1 日 20,000 回まで | 1 日数回しか使わない |
| スプレッドシートは 1,000 万セルまで | 1 日あたり数百セル。数十年ぶんの余裕がある |

## 却下した案

| 案 | 却下理由 |
| --- | --- |
| クラウド関数 ＋ スケジューラ | 記録先との接続に認証が要る。無料枠を出る可能性もある |
| CI の定時実行 | 記録先への書き込みに認証情報を持たせることになる。**秘密を置く場所が増える** |
| 常駐サーバ | 受信する口を持たない仕組みに常駐は要らない。運用が重くなるだけ |
| ノーコードの連携サービス | 判定と通知ログの管理を表現しきれない。費用も月額で発生する |

## 影響

- [ARCH-01](../10-architecture/arch-01-monitor-overview.md): 自前で運用するサーバを持たない構成になる
- [ARCH-02](../10-architecture/arch-02-daily-batch.md): 実行時刻の揺れと 1 回の取得上限が、実行モデルの前提になる

**リポジトリを正とする。** 配置は CI から自動で行うため、
実行基盤の編集画面で直接コードを書き換えない。書き換えても次の配置で消える。

## 見直しの条件

- 監視対象が増えて 1 回の実行が 6 分に収まらなくなったとき
- 受信する口（Webhook や問い合わせへの応答）が必要になったとき
- 記録先をスプレッドシート以外に移すとき。**この決定の前提が丸ごと崩れる**
